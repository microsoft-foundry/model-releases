# Demo Skills Plan — `add-demo` + `run-demo`

> Companion design doc for two new skills under [`.agents/skills/`](../.agents/skills/) that let a **speaker** turn any workshop in this repo into a tight, repeatable on-stage or pre-recorded demo. Reference example for validation: the **BRK230 45-min breakout** flow in [`.do-not-commit/Notes-v1.md`](../.do-not-commit/Notes-v1.md), which already enumerates demos **D1 – D5** drawn from [`workshops/foundry-models-e2e/`](../workshops/foundry-models-e2e/).

---

## 1. Goal

Make it **as easy as possible** for a speaker to:

1. **Plan a demo** from an existing workshop in this repo and capture it as a single, refreshable spec — one row per beat, with description / duration / theme / takeaway / steps-to-record — so a recording crew or live presenter can execute it cold.
2. **Run that demo** later — either to record, or to present live — with a Copilot session that reveals one beat at a time, holds a scorecard between beats, and ends on a clean takeaway.

The two skills are independent but pair naturally: `add-demo` writes the spec; `run-demo` reads it. Both stay aligned with the repo's existing skill conventions ([`add-workshop`](../.agents/skills/add-workshop/SKILL.md), [`run-workshop`](../.agents/skills/run-workshop/SKILL.md)).

## 3. `demos/<id>/` folder layout

```
demos/
  .gitkeep
  SESSIONS.md                 # named Copilot sessions registry (optional, speaker-curated)
  <id>/                       # unique speaker-chosen id, e.g. D1, brk230-d1, keynote-router
    demo.md                   # THE SPEC — single source of truth, see §6
    README.md                 # short landing page: title, duration, how to run, links
    transcript.md             # stub the speaker fills in (or auto-drafted from beats)
    recordings/
      .gitkeep                # binaries (mp4/mov) are gitignored
    slides/                   # optional MARP deck for the cut-in segment
      index.md
    assets/                   # screenshots, GIFs, fallback stills, etc.
      .gitkeep
    .state.json               # runtime state for `run-demo` (gitignored)
```

- **`id` rules:** kebab-case, `^[a-z0-9][a-z0-9-]*$`, max 32 chars. Speaker picks; skill validates and refuses collisions. The id is also the suggested session name (see §8).
- The folder must contain `demo.md` to be considered a valid demo. Everything else is optional and scaffolded with placeholders.

## 4. `add-demo` skill

### 4.1 When to use

- "Create a demo from the foundry-models-e2e workshop."
- "Add a new demo for the BRK230 router segment."
- "Refresh demo `D5` against the latest workshop."

### 4.2 Modes

| Mode | Trigger | Behavior |
|---|---|---|
| **Create** | `demos/<id>/` does not exist. | Run the full interview, generate the folder. |
| **Refresh** | `demos/<id>/demo.md` already exists. | Re-read it, re-read referenced workshop files, regenerate auto-derivable sections (file links, code excerpts, scorecard numbers, "steps to record" suggestions), **preserve** speaker-authored sections (theme, takeaway, narrator beats, recording notes). Surface a diff summary at the end. |

The refresh mode is the key durability play: as the workshop evolves (file renames, scorecard updates, new sample data), the demo spec is just re-rendered, not re-written.

### 4.3 Interview (create mode)

Ask in order, one question at a time, using `ask_user`-style turns:

1. **`workshop_slug`** — pick from `workshops/*/` (list folders). Required.
2. **`id`** — kebab-case unique id. Validate; if collision, suggest `<id>-v2`.
3. **`title`** — short human title (≤ 80 chars).
4. **`session_context`** *(optional)* — free text like "BRK230 Stanza 2 – SELECT". Stored verbatim so the demo plugs into a larger flow.
5. **`target_duration`** — `m:ss`. Validate `^\d{1,2}:[0-5]\d$`.
6. **`theme`** — one sentence: the *idea* the demo lands.
7. **`takeaway`** — one sentence: what the audience should *remember* afterwards.
8. **`source_steps`** — multi-select from the workshop's numbered step files (`00-…` … `99-…`). Default offering: all steps. Speaker picks the ones the demo draws from.
9. **`mode_hint`** — `portal | code | mixed`. Used by `run-demo` to pick presentation style.
10. **`held_end_frame`** — short description of the final on-screen artifact (e.g. "v1 → v3 scorecard"). Used by `run-demo` to know when to stop.

The skill then **reads the chosen source files** and auto-proposes a numbered "Steps to record" shot list. The speaker accepts, edits inline, or re-prompts.

### 4.4 Output (rendered files)

- `demos/<id>/demo.md` — full spec, frontmatter + sections (see §6).
- `demos/<id>/README.md` — landing page: header card + "How to run" pointing at `run-demo`.
- `demos/<id>/transcript.md` — stubbed transcript with one heading per beat; speaker fills in voiceover later.
- `demos/<id>/recordings/.gitkeep`, `demos/<id>/assets/.gitkeep`.
- `demos/<id>/slides/index.md` — **only if** the speaker answers yes to "include a MARP cut-in deck?" (delegates to existing [`create-slides`](../.agents/skills/create-slides/SKILL.md) skill).

### 4.5 Refresh mode behavior

1. Load `demos/<id>/demo.md`, parse frontmatter + sections.
2. Re-resolve every workshop file path under `source_steps`. For each:
   - If renamed, propose the rename and apply on confirmation.
   - If deleted, flag as a `⚠ broken source` row.
3. Re-derive: code excerpts, file links, mentioned scorecard numbers (regex `quality \d`, `\$\d+\.\d+`, `p50 \d+(\.\d+)?\s*s`).
4. **Never overwrite** speaker-authored sections: `## Theme`, `## Takeaway`, `## Narrator beats`, `## Recording notes`. The skill diffs and leaves these untouched.
5. End with a delta summary: "3 file links updated · 1 scorecard number updated · 0 broken sources · 0 author sections touched."

### 4.6 Guardrails

- Refuse if no `workshops/*/` exist.
- Refuse to overwrite `demo.md` outside refresh mode.
- Never write binary files. Recordings live in `recordings/` and are gitignored.
- Keep examples Foundry / Azure-direct. Do not name competitor clouds. Use inclusive language ("key points" / "sentences", not "bullets").

## 5. `run-demo` skill

### 5.1 When to use

- "Run demo `D3` for me."
- "Walk me through `demos/<id>` so I can record it."
- "I'm going live in 5 minutes — start the BRK230 router demo."
- "Resume the demo I paused."

### 5.2 Modes

| Mode | Pace | Output style | Use case |
|---|---|---|---|
| **`live`** *(default)* | Lean. One beat at a time, ≤ 5 lines per beat. | Tabular scorecards, emoji status (▶ now · ✅ done · ⏸ paused · 🎯 takeaway), no "READY?" prompts. | Speaker is on-stage and reads the chat to stay on track. |
| **`record`** | Deliberate. Includes "READY?" pause prompts, suggested mouse parking spots, held-frame timers. | Same visual style plus shot framing notes. | Speaker is recording a clip alone with screen capture running. |

Mode is asked once at start, persisted in `.state.json`.

### 5.3 Subskills

| Subskill | Use when |
|---|---|
| `start` | New session; pick demo, confirm mode, show header card. |
| `next-beat` | Reveal the next beat from `demo.md` and update `.state.json`. |
| `prev-beat` | Step back one beat (useful in record retakes). |
| `show-scorecard` | Re-print the demo's current scorecard at any time. |
| `pause` / `resume` | Save state, exit cleanly, or resume from saved beat. |
| `recap` | Show the held-end-frame description + the one-line takeaway. |
| `troubleshoot` | If a live command fails, fall back to the recorded clip listed in `recordings/` and continue. |

### 5.4 Header card (rendered at `start` and `recap`)

```
╭─ Demo D3 · Multi-model decomposition ─────────────────╮
│ ⏱  target 2:30        🎯 theme: right model per job   │
│ 📺 mode: live          📂 workshop: foundry-models-e2e│
│ 🧭 beats: 4            🪧 ends on: updated scorecard  │
╰───────────────────────────────────────────────────────╯
```

### 5.5 Beat card (rendered at every `next-beat`)

```
▶ Beat 2 of 4 · 00:45 cumulative · ~0:40 budget
─────────────────────────────────────────────────────────
Run the same Carmen prompt; show the trace fan-out.

  $ python workshops/foundry-models-e2e/code/s05_multi_model_agent.py

🎯 Audience should see: router → policy + planner spans.
🪧 End on: trace timeline view.

✅ Mark done?  ⏭ next  ⏸ pause  ↩ prev
```

### 5.6 Scorecard rendering rules

- Always render as a markdown table (consistent across demos).
- Use subtle, semantic emoji **only** as status indicators: ✅ improvement, ⚠ regression, ➖ neutral. No decorative emoji in numbers.
- Bold the **delta** column.
- Limit to ≤ 4 rows per scorecard so it fits in a single Copilot Chat viewport at standard font size.

Example:

| Metric | v1 baseline | v3 optimized | **Δ** | |
|---|---|---|---|---|
| Quality | 0.41 | 0.46 | **+12 %** | ✅ |
| Cost / req | $0.023 | $0.006 | **−74 %** | ✅ |
| p50 latency | 12.5 s | 6.5 s | **−48 %** | ✅ |

### 5.7 Reveal-only-the-next-beat rule

Same discipline as `run-workshop`: never paste the full `demo.md` into the chat. The speaker should only ever see the current beat plus the header card. Future beats are revealed by `next-beat`.

### 5.8 Runtime state

`demos/<id>/.state.json` (gitignored):

```json
{
  "demo_id": "D3",
  "mode": "live",
  "started_at": "2026-05-29T09:00:00Z",
  "current_beat": 2,
  "completed_beats": [1],
  "paused": false,
  "session_name": "demo-D3-router"
}
```

## 7. Named Copilot sessions

The speaker will usually drive `run-demo` from one of:

- **Copilot CLI** — `copilot --session demo-<id>` (e.g. `demo-D3-router`).
- **Copilot Chat in VS Code** — name the chat via the gear menu using the same convention.

`run-demo/start` should:

1. Ask: "How will you run this — Copilot CLI or Copilot Chat?"
2. Propose the session name `demo-<id>-<slug-of-title>` (e.g. `demo-D3-multi-model-decomp`).
3. Persist it in `.state.json` and append a row to `demos/SESSIONS.md` (the optional human-readable registry):

   | Demo | Session name | Surface | Last used |
   |---|---|---|---|
   | D3 | `demo-D3-multi-model-decomp` | Chat | 2026-05-29 |

`SESSIONS.md` is committed; `.state.json` is not.

## 8. Visual / tone rules for both skills

These apply to every message `run-demo` emits and to all generated `demo.md` content:

1. **One beat at a time.** Never dump the full spec.
2. **Tabular over prose** for scorecards, comparisons, and headers.
3. **Subtle color via emoji** — only as status indicators: ✅ ⚠ ➖ ▶ ⏸ 🎯 🪧 ⏱ 📺 📂 🧭. No decorative emoji.
4. **Concise takeaways** — one sentence, present tense, audience-facing.
5. **Inclusive language** — "key points", "sentences", not "bullets".
6. **No competitor cloud names.** Foundry / Azure-direct examples only.
7. **Held end frame is sacred** — every demo must declare one, and `run-demo recap` must end on it so the cut back to the speaker is clean.

## 9. Validation plan — reproduce BRK230 D1 – D5

The acceptance test for both skills is: re-create the five demos already enumerated in [`.do-not-commit/Notes-v1.md`](../.do-not-commit/Notes-v1.md) §`DEMO VIDEOS – PRE-RECORDED` and confirm the generated `demo.md` files reproduce that table.

Procedure:

1. With both skills in place, run `add-demo` five times against `foundry-models-e2e`, supplying the IDs **D1, D2, D3, D4, D5** and the inputs already specified in `Notes-v1.md`.
2. After generation, diff each `demos/D<n>/demo.md` against the corresponding row in `Notes-v1.md`. Acceptance:
   - Duration, theme, takeaway, source_steps, and held_end_frame match exactly.
   - "Steps to record" lists are equivalent (auto-numbering + minor wording allowed).
3. Run `run-demo` on **D3** end-to-end in `live` mode; capture a transcript of the chat output. Acceptance: ≤ 5 lines per beat, one scorecard rendered, ends on the held end frame.
4. Edit one source file (e.g. rename `s05_multi_model_agent.py` to `s05_multi_agent.py`), run `add-demo` in refresh mode against **D3**, and confirm the file link is updated while `## Theme`, `## Takeaway`, `## Narrator beats`, and `## Recording notes` are unchanged.
5. Confirm all five `demos/D<n>/` folders pass the lint:
   - `demo.md` parses (frontmatter + required sections present).
   - `README.md` exists with the header card.
   - `recordings/.gitkeep` exists; no `.mp4`/`.mov` is committed.

Once steps 1–5 pass, the demo skills are considered correct against the BRK230 reference.

## 10. Out of scope (for now)

- Auto-rendering MP4 from `demo.md` (we link out to `create-slides` for MARP only).
- Live-screen automation (Playwright / Selenium). Speakers still drive their own VS Code and browser.
- Speech-to-text transcript capture. `transcript.md` is authored by the speaker after recording.
- Cross-workshop demos (one `demo.md` referencing two workshops). v2 if needed.

## 11. Open questions for the speaker to confirm before build

1. **`id` namespacing** — keep flat (`D1`, `D2`, …) or prefix per session (`brk230-d1`)? **Default:** flat, with `session_context` capturing the breakout.
2. **Scorecard auto-extraction** — for v1, parse from referenced `eval_results_*.json` files in the workshop's `code/` folder? Or always author by hand? **Default:** auto-draft, speaker edits.
3. **Sessions registry** — is `demos/SESSIONS.md` worth committing, or keep entirely local? **Default:** committed, lightweight.
4. **MARP cut-in deck** — generate per demo, or one shared deck for the whole session? **Default:** per demo, optional.
5. **`run-demo` mode default** — `live` (lean) or `record` (deliberate)? **Default:** `live`; speaker explicitly opts into `record` when capturing.
